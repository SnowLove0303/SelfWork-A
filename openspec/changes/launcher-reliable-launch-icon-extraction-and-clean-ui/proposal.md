# Proposal: 启动器原生可靠唤起、应用图标动态提取与极简卡片视觉纯净化

## 1. 意图与背景 (Intent & Context)
用户在实测重构后的快速启动工作台时提出了关键反馈与改进诉求：
1. **运行不了**：点击微信、飞书、Antigravity 等应用无反应或闪退，根因在于 Windows 命令行双重引号截断及未自动继承应用父目录导致同级 DLL 缺失；
2. **应用图标缺失**：卡片上只有千篇一律的通用占位图标，期望能够自动提取本地应用（`.exe` / `.lnk`）的原生高品质官方图标；
3. **视觉冗余杂乱**：卡片上铺满了长长的磁盘物理路径和多余说明文本，期望界面极简清爽，非必要路径不直接展示在卡片表面，仅在编辑/设置中可见。

## 2. 1:1 需求物理对账矩阵 (RTM)

| 需求编号 | 用户原始诉求条目 | 拟定解决方案与落地点 | 验收标准 [Measured] |
| :--- | :--- | :--- | :--- |
| **REQ-FIX-01** | **应用程序点击可靠唤起修复**<br>“运行不了啊” | 1. 重构 Rust 原生 IPC `launch_custom_target`，可执行文件直接原生启动，未指定工作目录时自动缺省推导为该 exe 的父目录（`parent()`），彻底解决同级 DLL 缺失闪退；<br>2. 对快捷方式（`.lnk`）、目录与网页采用 Windows 原生 Shell 唤起，杜绝 cmd 双引号逃逸。 | 点击微信、飞书、Antigravity、Xmind 等卡片，对应的 Windows 桌面客户端真实打开呈现在前台，退出码 0。 |
| **REQ-FIX-02** | **本地应用原生图标自动提取与卡片展示**<br>“能不能想办法拿到应用的图标放上去” | 1. 在 Rust 后端提供原生 IPC `get_app_icon(target)`，基于 Windows 系统能力从 `.exe` / `.lnk` 提取 32x32 / 48x48 高品质 PNG Base64；<br>2. `LauncherItem` 增补 `icon?: string` 契约，前端自动拉取并持久化记忆，冷启动秒开呈现；<br>3. 脚本、网页或提取失败时平滑回退语义晶体图标。 | 微信、飞书、Antigravity、Xmind、Chrome 等卡片中心清晰呈现官方彩色高清图标，重启后依然保留。 |
| **REQ-FIX-03** | **卡片说明与长路径展示纯净化**<br>“尽量不要有非必要的说明，包括路径这些，不要直接显示出来，对应的设置能看就行了” | 1. 重构卡片网格布局，彻底剔除卡片表面暴露的长物理路径文本与次要描述段落；<br>2. 卡片收敛为：**高品质应用图标 + 精炼标题 + 状态响应 + 悬浮操作菜单**；<br>3. 物理路径、运行参数、工作目录完全收敛在“编辑启动项”模态框中供用户查看与修改。 | 卡片表面 0 暴露长路径字符串，排版极简高级；点击编辑弹窗可完整查看和修改路径设置。 |
