# Change Proposal: 快速启动分屏多显示器精准投送与几何划分根治 (fix-launcher-split-screen-multimonitor-tiling)

## 1. 背景与问题定义
在 SelfWork 快速启动模块中，用户使用组合分屏或多选即时分屏启动时，观察到两大核心阻断问题：
1. **未正确在对应分屏启动**：配置定向投放至副屏（如“屏幕 2”）或主屏时，拉起的应用程序与文件夹未被移动至指定屏幕，仍停留于系统默认屏幕；
2. **未进行屏幕划分**：拉起后的窗口维持默认尺寸或最大化状态，未按预设布局（如左右双分屏 1:1、田字四分屏 1/4×4）进行无缝几何网格划分。

通过 5-Whys 深度穿透，定位到根本原因如下：
- **致命根因 1 (解释器语法中断)**：`src-tauri/src/lib.rs` 的跨会话窗口枚举逻辑中混入了 Windows PowerShell 5.1 不支持的 `&&` / `||` 语法标记，导致底层脚本在装载期直接遭遇语法解析异常（ParserError），执行流瞬间中断，`SetWindowPos` 坐标设置动作 100% 被跳过；
- **致命根因 2 (弱断言欺诈与静默吞没)**：Rust 端在读取 PowerShell 输出时使用 `.unwrap_or(specs.len())`，将进程崩溃静默伪装成全量匹配成功，导致前端 UI 虚假提示成功；
- **致命根因 3 (进程名与窗口标题匹配脆弱)**：对应用程序（如 `chrome.exe`、`msedge.exe`、`WeChat.exe`）的匹配仅基于带 `.exe` 后缀的名称，而 Windows 进程主窗口标题通常为应用中文名或文档名，系统 `ProcessName` 亦不带 `.exe`，导致即使脚本运行也可能发生匹配落空。

## 2. 1:1 需求物理对账矩阵 (RTM)

| 需求 ID | 用户原始需求条目 | 核心问题归因定性 | 目标行为契约 | 验收物理指标 |
| :--- | :--- | :--- | :--- | :--- |
| **REQ-SNAP-01** | **1. 未正确在对应分屏启动** | 跨屏幕（主屏/副屏）定向投送失效，应用与文件夹停留于系统随机默认屏幕 | 用户选定目标显示器（如屏幕 1 主屏、屏幕 2 副屏）后，被唤起的全部窗口 100% 跨屏移动至所选显示器的工作区范围内，严禁跨屏漂移或滞留原屏 | 目标窗口的物理坐标 (X, Y) 严格落入选定显示器可用工作区（Working Area）绝对边界内，副屏投放绝对不在主屏滞留 |
| **REQ-SNAP-02** | **2. 未进行屏幕划分** | 窗口尺寸未被裁剪，未形成左右双分屏或四分屏几何平铺 | 启动后各窗口根据预设布局（左右双分屏 50%:50%，或四分屏 25%×4）自动解除最大化，并以像素级精度调整宽、高和坐标，各子窗口边缘紧密贴合且零重叠 | 窗口尺寸 (Width, Height) 与屏幕工作区比例严格吻合；平铺后各窗口之间零重叠、零遮挡，形成整齐的屏幕几何网格 |

## 3. 拟变范围与影响半径
- `src-tauri/src/lib.rs`: 修复 PowerShell 语法兼容性；增强 Rust 端退出码审计（非 0 即报错，严禁伪通）；引入进程名、程序无后缀名（Stem）、前端条目别名（ItemName）与窗口标题的多维健壮模糊匹配；
- `src/components/LauncherDashboard.tsx`: 在向 `arrange_combo_windows` 传递参数时，将条目的友好显示名称（`name`）同步注入 `WindowPlacementSpec`；优化唤起后的等待时序与多轮探测时间。
