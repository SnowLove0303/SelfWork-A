# Change Proposal: 修复便签删除持久化与首发初始化生命周期 (fix-memo-deletion-persistence-lifecycle)

## 1. 变更背景与事实指纹
- **需求事实指纹**: `USER_PROMPT_SHA256: 3c57e87ab0cfc22b9195977921a971d2b8b9cb0be555c2d33c829e1f57004d80`
- **用户原始反馈**: `还是不行，我删除的默认便签在重新打开后又恢复了`
- **问题根因 (5-Whys)**:
  1. 便签/待办加载逻辑使用 `sqliteMemos.length > 0` 判定是否有数据；
  2. 当用户删除全部便签（或删除默认便签致空）后，`length === 0` 被错误判定为“从未初始化的全新安装”，强制触发 `saveMemos(INITIAL_MEMOS)` 重新灌入种子便签；
  3. `TasksView.tsx` 组件在挂载时如果直接以 `INITIAL_MEMOS` 初始化并在 `loadMemos()` 完成前误触发自动持久化，会造成覆盖回写；
  4. 缺少显式持久化的 `memos_initialized` 与 `tasks_initialized` 生命周期里程碑标记。

## 2. 1:1 需求物理对账矩阵 (RTM)

| 条目编号 | 需求描述 | 验收指标 |
| :--- | :--- | :--- |
| **RTM-REQ-01** | **便签删除操作跨重启绝对物理持久化**<br>已被删除的便签（包括默认预置便签）在冷重启后绝不复原。 | 1. 删除便签后彻底关闭进程；<br>2. 重新启动应用，已删除便签 100% 保持删除状态，绝不复活。 |
| **RTM-REQ-02** | **清空/全删状态的绝对持久**<br>用户清空所有便签或待办后，列表为空状态必须持久有效。 | 1. 便签列表清空后重启，列表保持为 0 项；<br>2. 待办列表清空后重启，列表保持为 0 项；<br>3. 杜绝将空列表判定为未初始化。 |
| **RTM-REQ-03** | **显式生命周期状态解耦**<br>在物理数据库 `app_settings` 表中建立 `memos_initialized` 与 `tasks_initialized` 强持久标记。 | 1. 仅在首次开机未初始化时执行一次种子注入；<br>2. 一旦标记生效，无论数据有多少条（包括 0 条），以物理库为绝对法定准则，禁止重填。 |
| **RTM-REQ-04** | **删除操作即时原子提交**<br>删除和清空操作跳过 300ms 防抖等待，执行即时物理持久化提交。 | 1. 点击删除瞬间直接触发底层原子落盘；<br>2. 杜绝 300ms 防抖期间窗口快速关闭导致未落盘。 |
